# TRS-398 Rev.1: платформа определения абсолютной дозы

> **Версия 2.0:** вместо Docker и PostgreSQL используется один файл SQLite (`app/migrations/001_baseline.sql`). Роли и функции SECURITY DEFINER заменены триггерами (защита утверждённых записей, журнала аудита, номеров протоколов) и служебными операциями `app/dbops.py`. Разделы о Docker и ролях PostgreSQL описывают версию 1.x (ветка `v1.x`); расчёты и модель данных те же.

Перенос двух xlsm-таблиц (фотоны HE v2.0, электроны HE v2.0) в Docker + PostgreSQL с трендами.
Статус: реализовано (см. README); документ хранит разбор исходных таблиц и принятые решения. English: [DESIGN.en.md](DESIGN.en.md).

## 1. Что на самом деле делают макросы

Расчёт TRS-398 в таблицах сделан **формулами листа и именованными диапазонами**, а не VBA.
Макросы делают три вещи, и только третья нужна платформе как логика.

### 1.1 Интерфейс таблицы (в платформе не нужен)
- ~25 обработчиков `CheckBox*_Click` переключают режимы: SSD/SAD, импульсный/сканирующий пучок,
  полярность, способ получения TPR, FFF/WFF. Они меняют скрытый лист «Черновик», показывают и
  прячут объекты, красят и блокируют ячейки (`Locked`, `Interior.ColorIndex`).
- `Worksheet_Change` (лист «Расчёт»): предупреждение, если |RHo − RH| ≥ 30 (влажность
  при измерении и при калибровке); пересчёт блокировки PDD20 при смене фильтра (I8).
- `Workbook_Open`: показывает листы, ставит защиту. `Workbook_BeforeClose`: диалог сохранения.
- `modFixRU2.Fix_Formatting_Rev1`: правит русские подписи и верхние/нижние индексы.
- В платформе это заменяется обычной формой с валидацией и условными полями.

### 1.2 Защита (в платформе заменяется настоящими ролями)
- Структура книги и листы защищены паролями, которые **зашиты в коде** (`heslo`, `WB_PASSWORD`).
  Это защита от случайной порчи, а не от доступа: код читается из xlsm без пароля.
- Следствие: пароли из таблиц в платформу не переносим, аутентификация и роли делаются заново (раздел 3).

### 1.3 Журнал и тренды (`LogDose`, перенос логики обязателен)
- `AddToLog`: берёт текущий расчёт (строка 3 «Журнала») и дописывает запись в таблицу
  `ЖурналТбл`: дата, камера, MQ, Dw(zref), Dw(zmax), kTP, kelec, kpol, ks, kvol, kQ, ND,w, TPR20,10
  плюс примечание (исполнитель, № протокола). Предупреждает о дубле (та же дата и та же Dw).
- `DeleteJournalRows`: удаляет выбранные записи после подтверждения (необратимо).
  После удаления все формулы пересобираются (`RebuildAllFormulas`).
- Большая часть кода `LogDose` обходит особенности Excel: самонарастающие диапазоны
  портили соседние строки, поэтому формулы пишутся текстом. **В БД этой проблемы нет.**

Формулы журнала, которые нужно сохранить:

| Величина | Формула |
|---|---|
| Отклонение от 1 сГр/MU, % | `(Dw_zmax − 0,01) / 0,01 · 100` |
| Отклонение от предыдущего, % | `(Dw − Dw_пред) / Dw_пред · 100` |
| MR (скользящий размах) | `abs(откл_i − откл_{i−1})` |
| CL | среднее отклонений (по всем записям) |
| σ | `MR̄ / 1,128` |
| ±2σ, ±3σ | `CL ± 2σ`, `CL ± 3σ` |
| UCL(MR) | `3,267 · MR̄` |
| Сигнал SPC | точка за 3σ; 2 из 3 последних за 2σ по одну сторону; 8 подряд по одну сторону от CL |
| CUSUM | `k = 0,5σ`, `H = 5σ`; `C+_i = max(0, C+_{i−1} + (x−CL) − k)`, `C−_i = min(0, C−_{i−1} + (x−CL) + k)` |
| Статус | `\|откл\| > 2 %` действие; `> 1 %` наблюдение |
| Тренд, %/мес | `SLOPE(откл, дата) · 30,4375` |
| Прогноз выхода за ±2 % | пересечение линии тренда с ±2 % |
| Тренд kelec | значения kelec из записей по времени (поверки) |

Нюансы, которые стоит решить осознанно (в xlsm они неявные):
- CL и σ считаются по **всем** записям и сдвигаются с каждой новой точкой. Для SPC обычно фиксируют
  базовый период. В платформе: `spc_baseline` с датами начала и конца, пересчёт по запросу.
- Сигнал 2 из 3 и 8 подряд привязан к номеру записи, а не к дате. В БД использовать порядок по дате.

## 2. Формулы расчёта (на листах, не в VBA)

### Фотоны (раздел 6 Rev.1)
- `kTP = (P0/P) · (273,2 + T)/(273,2 + T0)`
- `kpol = (|M+| + |M−|) / (2·M)`; если Q ≠ Q0: `kpol / kpol_Q0`
- `ks = a0 + a1·(M1/M2) + a2·(M1/M2)²`, коэффициенты `a0..a2` линейной интерполяцией по V1/V2 из Таблицы 10
  (отдельные наборы для импульсного и сканирующего пучка)
- `kvol` (только FFF): `1 + (0,0062·TPR20,10 − 0,0036)·(100/SCD)²·L²`, `SCD = SSD + zref`, L из паспорта камеры
- Качество пучка:
  - WFF: `TPR20,10 = 1,2661·(PDD20/PDD10) − 0,0595`
  - FFF: `TPR20,10 = −0,7898 + 0,0329·PDD10 − 0,000166·PDD10²`
  - допустимый диапазон Таблицы 16: 0,56–0,82 (вне диапазона kQ не определён)
- `kQ` по Таблице 16 (26 камер, 12 узлов TPR от 0,56 до 0,82), **линейная интерполяция** (VBA `Interpolate`)
- `M_corr = M1 · kTP · kelec · kpol · ks · kvol`; `Dw,Q(zref) = M_corr · ND,w · kQ,Q0`
- `Dw(zmax)`: SSD `= 100·Dw(zref)/PDD(zref)`; SAD `= Dw(zref)/TMR(zref)`
- Контроль «1 сГр/MU»: `Dw(zmax)·100`, поправка в %, значение на 200 MU

### Электроны (раздел 7 Rev.1)
- `R50` измеренный; `Q (R50,w) = коэф · R50 · 1,029 − 0,06` (лист Temp)
- `zref = 0,6·R50 − 0,1`
- `kQ` из Таблиц 20 (калибровка в 60Co) и 21 (калибровка в электронном пучке), 16 камер, сетка R50 из 14 узлов
  (1,0 … 10 г/см²), **натуральный кубический сплайн** (в `modRev1kQ` проверен против scipy, расхождение < 1e-15)
- `Dw` по тем же k-факторам (kTP, kpol, ks, kelec)

### Неопределённость
Отдельный лист «Неопределённость» в обоих файлах. В первой версии платформы выводим в отчёте как есть,
расчёт переносим вторым этапом (см. план).

## 3. Роли и доступ

Два слоя: роли приложения (что может человек) и роли БД (что может сервис).

### 3.1 Роли приложения (RBAC)

| Роль | Кто | Права |
|---|---|---|
| `viewer` | любой сотрудник отделения | смотреть измерения, тренды, отчёты |
| `physicist` | медицинский физик | всё из `viewer`, плюс создавать и редактировать **свои черновики**, отправлять на проверку |
| `reviewer` | старший физик / второй проверяющий | всё из `viewer`, плюс утверждать или возвращать записи. **Не может утвердить собственную запись** |
| `admin` | ответственный за систему | пользователи и роли, справочники (камеры, kQ-таблицы), аппараты, базовый период SPC, пороги тревог |

Правила:
- Статусы записи: `draft → submitted → approved` (либо `returned → draft`). В тренд и SPC попадают
  **только утверждённые**.
- Утверждённая запись неизменяема. Исправление создаёт новую запись, ссылающуюся на старую
  (`supersedes_id`), старая получает статус `superseded` с обязательной причиной. Физического удаления
  нет, это заменяет макрос «Удалить записи».
- Принцип двух лиц: `approved_by ≠ created_by` (CHECK в БД).
- Справочники (kQ, ND,w, камеры) версионируются: каждый расчёт хранит версию таблиц и версию формул,
  чтобы результат можно было воспроизвести.
- Журнал аудита (`audit_log`) только на добавление (запрещено UPDATE и DELETE триггером).

### 3.2 Роли PostgreSQL
| Роль БД | Для чего | Права |
|---|---|---|
| `trs_owner` | миграции | владелец схемы, DDL |
| `trs_app` | приложение | `SELECT/INSERT/UPDATE` на рабочие таблицы, только `INSERT` в `audit_log`, нет `DELETE` |
| `trs_readonly` | Grafana, аналитика | `SELECT` на представления (`v_trend`, `v_spc`), без доступа к пользователям и хэшам паролей |

Пароли ролей БД (версия 1.x) брались из `.env`. Пароли пользователей приложения хранятся
только хэшем (argon2/bcrypt).

## 4. Модель данных (кратко)

Справочники: `chambers`, `chamber_kq_photon`, `chamber_kq_electron`, `electrometers`, `linacs`, `beams`.
Оборудование и поверки: `chamber_units` (SN), `calibrations` (ND,w, kelec, лаборатория, дата).
Измерения: `measurement_sessions` (входные данные), `results` (все k-факторы, Dw, отклонение, версии).
Контроль качества: `spc_baseline`, представления `v_trend`, `v_spc`.
Служебное: `users`, `audit_log`.

Схема в `db/init/001_schema.sql`.

## 5. План работ

1. **Расчётное ядро** (чистый Python) с тестами: фотоны, потом электроны. Эталон: ваши xlsm
   (фотоны 6 FFF: kQ = 0,99726616; ks = 1,00299564; kvol = 1,00124046; kTP = 1,01031742; Dw(zmax) = 0,0100012639 Гр/MU).
2. **БД и роли**: схема, миграции, импорт справочников и журналов из xlsm.
3. **Веб-приложение**: ввод измерения, расчёт, отправка на проверку, утверждение.
4. **Тренды**: SPC на данных БД (правила из раздела 1.3), Grafana по `v_trend`.
5. **Отчёты PDF и неопределённость.**

## 7. Результаты проверки (Oct 2026)

- Ядро фотонов и электронов совпадает с сохранёнными значениями xlsm (тесты `tests/test_photon.py`, `tests/test_electron.py`).
- SPC (`core/spc.py`): CL, наклон тренда и последнее отклонение совпали с листом «Тренд».
- **В xlsm фотонов SPC-столбцы журнала не считаются.** Формулы «№ записи», «пред. Dw», «пред. откл.» стоят в
  столбцах I, J, K, а формулы MR, «Сигнал SPC» и CUSUM ссылаются на J, K, L (сдвиг на один столбец после
  удаления столбца). Из-за этого MR пуст, σ в «Тренде» пуста, лимиты ±2σ/±3σ и CUSUM дают `#N/A`,
  а «Сигнал SPC: нет» показывается всегда. Python-расчёт находит сигнал «за 3σ» на записи 14 (2024-12-14,
  +0,82 %), и именно к ней в журнале приложена ручная заметка о сигнале «за 3σ».
- Электронный журнал (25 записей) помечен «Demo data»: импортирован с флагом `is_demo`, в тренды не попадает.
- Исторические журналы содержат только итоги (без показаний), поэтому лежат в `legacy_journal`.

## 8. Неопределённость и интерактивные графики

- `core/uncertainty.py`: бюджет по TRS-398 Rev.1 (Табл. 17 для фотонов, Табл. 24/25 для электронов, раздел 7.10),
  тип A = σ журнала (MR̄/1,128), объединение в квадратуре, U = 2·uc, вклады составляющих, решение о перекалибровке
  (вердикт по допуску и U_отн = 2·√2·σ, тренд, месяцы до уровней, рекомендуемая дата). Числа листов воспроизводятся
  до последнего знака (`tests/test_uncertainty.py`).
- Страницы `/trends` (график Plotly с запасным серверным SVG) и `/uncertainty` (диаграмма вкладов Plotly).
- Находки в исходных xlsm:
  - фотоны: итоговые ячейки листа «Неопределённость» (`uc`, `U`) показывают `#VALUE!`, так как тип A берётся из
    «Тренда» (D5), а он пуст из-за сдвига столбцов журнала (см. раздел 7);
  - электроны: условие «R50 текущего пучка» использует именованный диапазон `R_50`, который указывает на пустую ячейку
    (R50 калибровочного пучка), поэтому для плоскопараллельной камеры всегда берётся значение для R50 < 2 г/см² (0,8 %).
    В платформе используется R50 измеряемого пучка (0,7 % при R50 ≥ 2 г/см²); это отличие от листа осознанное.

## 9. Протокол и приложение «Оценка неопределённости»

- Протокол (`app/protocol.py`, `app/templates/protocol.html`) воспроизводит лист «Расчёт» (цвета ячеек, формулы, галочки,
  блок «Примечание: 1cGy=1MU check», сноски a–f) в A4; в Excel тот же лист разваливается на 6 страниц по ширине.
- Приложение к протоколу строится по листу «Неопределённость» из файла электронов вместе с его комментариями:
  конфигурация, этапы 1 и 2 (тип B, жёлтые ячейки), тип A (σ журнала на дату измерения), uc и U (k = 2), справочное значение
  TRS-398, определения GUM, примечания (a)–(e) для электронов и (a)–(d) для фотонов, блок «Решение о перекалибровке».
  Тексты вынесены в `core/uncertainty_text.py`, расчёт в `core/uncertainty.py`, данные блока в `protocol.uncertainty_block()`.
- История для типа A и тренда: утверждённые и импортированные записи пучка до даты измерения плюс сама запись, если она ещё
  не утверждена; если для пучка задан базовый период SPC, используется он.
- Сверка с сохранёнными значениями листа электронов: тренд 0,142 %/мес, отклонение по линии тренда 0,554 %, U_отн 1,44 %,
  σ 0,51 % совпадают; uc отличается намеренно (см. раздел 8, ссылка `R_50` в исходном листе).
- `tools/render_sample.py` рисует образцы протоколов (синтетические данные) внутри контейнера для визуальной проверки.

## 11. Параметры оборудования и опорные показания

- Параметры разделов 1–3 листа задаются один раз в «Оборудовании» и на листе расчёта не меняются: у аппарата (модель, серийный №,
  город), у пучка (мощность дозы, размер поля или аппликатор, фантом, cpl, hpl, zmax), у калибровки (ND,w, Q0 и R50,w, глубина,
  P0, T0, влажность, V1, полярность при калибровке и «с поправкой», полярность у пользователя, лаборатория, даты, электрометр
  с серийным номером и диапазоном, галочка «калибруется отдельно» с kelec, лабораторией и датой).
- Расчёт берёт эти значения только из оборудования (`app/routes/measurements.py: equipment_values`), то, что прислал браузер, заменяется; снимок
  значений сохраняется в записи (`extra.form`), поэтому позднейшие правки оборудования не меняют старые протоколы.
- **kelec**: значение из свидетельства (например, ВНИИФТРИ) применяется только при галочке «калибруется отдельно от камеры»,
  иначе kelec = 1 (TRS-398 Rev.1, прим. c).
- **Показания (iii) и (iv)** (M+, M−, M при полярности пользователя, M1 при V1, M2, V1, V2, тип пучка) определяются один раз для
  пучка и камеры: форма подставляет их из первой утверждённой записи пучка, любое значение можно изменить. kpol и ks считаются по
  этим рядам (`PhotonInput.m_pol`, `m1_ks`), поэтому не зависят от величины текущего показания M1.
- Калибровку, уже использованную в измерениях, править нельзя (протоколы ссылаются на неё): добавляется новая калибровка.

## 12. Сравнение энергий

`core/compare.py` и страница `/compare`: ряды всех пучков аппарата сводятся по календарным месяцам (среднее за месяц). Общий сдвиг:
в месяце не менее 3 пучков с данными и не менее 70 % из них отклонились в одну сторону не менее чем на 0,3 %, при среднем не менее 0,3 %
(общая причина: монитор, среда, дозиметрия). Корреляция Пирсона по месячным отклонениям при не менее 6 общих месяцах. Подсказки
формулируются для физика и не заменяют решения. В демо-данных у TrueBeam есть сценарий общего сдвига (март–апрель 2026).
